## Problem

네트워크 프로그래밍 수업에서 여러 클라이언트가 접속하는 채팅 서버를 만들었다. 연결과 메시지가 동시에 들어올 때 소켓과 공유 상태가 어떻게 바뀌는지 이해하고 싶어 프로토콜부터 직접 구현했다.

처음에는 클라이언트마다 스레드를 하나씩 두고, mutex로 연결 목록과 브로드캐스트를 보호했다. 메시지를 전송하는 사이에 다른 스레드에서 소켓을 닫거나 목록의 노드를 삭제하면 닫힌 fd나 해제된 메모리에 접근할 수 있었다. 락을 넓게 잡으면 브로드캐스트가 직렬화되고, 좁게 잡으면 공유 상태의 일관성을 보장하기 어려웠다.

## Approach

### 프로토콜 구현

- **POSIX 소켓** — 소켓 생성, 주소 바인딩, 수신 대기와 연결 수락을 직접 처리했다.
- **HTTP 정적 서빙** — 응답 헤더, Content-Type, 본문을 구성해 채팅과 같은 포트에서 정적 파일을 제공했다.
- **WebSocket(RFC 6455)** — 핸드셰이크부터 프레임 마스킹과 가변 길이 처리까지 직접 구현했다. OpenSSL은 SHA-1과 Base64 처리에 사용했다.
- **JSON** — 자체 파서를 시도한 뒤, 메시지 스키마가 늘면서 안정성과 구현 시간을 고려해 cJSON으로 전환했다.

### 동시성 모델

클라이언트당 스레드를 두는 구조를 단일 스레드 epoll edge-triggered reactor와 비차단 I/O로 바꿨다. 긴 시간 연결된 채 대기하는 WebSocket 클라이언트마다 별도 스레드를 유지할 필요가 없었고, 한 스레드에서 I/O 이벤트와 연결 수명 주기를 처리할 수 있었다.

## Result

같은 포트에서 HTTP 정적 파일과 여러 클라이언트의 WebSocket 채팅을 처리했다. 이벤트 루프에서 연결 등록 해제, 소켓 닫기, 목록 제거와 메모리 해제를 순서대로 처리하도록 구성해 연결 목록에 대한 스레드 간 락을 제거했다.

## Insight

락의 범위를 정하기에 앞서 공유 상태를 한곳에서 관리할 수 있는지 살펴보는 게 중요했다. 프로토콜을 직접 작성하면서 디버깅 범위는 넓어졌지만, WebSocket의 마스킹과 가변 길이처럼 라이브러리 안에 가려진 동작을 이해할 수 있었다.
